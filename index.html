01

Repository

The project folder, tracked by Git and hosted on GitHub et al.

A repository ("repo") is your project folder plus its complete history. Git keeps every saved version inside a hidden .git directory, so you can see who changed what, when and why, and rewind if something breaks. Hosting the repo on GitHub (or GitLab, Bitbucket…) gives your team one shared place to collaborate, review and ship.

$ git init      # turn this folder into a repo
$ git status    # see what Git is tracking

Considerations

  • Add a .gitignore on day one so secrets, node_modules and OS junk like .DS_Store never get tracked.
  • Include a README.md that explains what the project is and how to run it. It's the repo's front door on GitHub.
  • Public vs. private matters: assume anything pushed to a public repo has been copied by someone, forever.
  • One repo per project is a good default. Monorepos (many projects in one repo) are a deliberate choice with their own tooling.

02

Clone

Download a copy of the code to your machine.

Cloning downloads a full copy of a hosted repository to your computer: every file, every branch and the entire commit history. Your copy works offline and remembers where it came from through a remote named origin, so you can push and pull later.

$ git clone https://github.com/you/my-website.git
$ cd my-website

Considerations

  • HTTPS or SSH? HTTPS needs a personal access token (or the GitHub CLI) to push. SSH keys skip the password prompts once they're set up.
  • Clone vs. fork: a clone is a copy on your machine. A fork is your own copy on GitHub, which you use when you can't push to the original.
  • For huge repos, git clone --depth 1 grabs only the latest snapshot. It's fast, but you won't have the history.
  • Run git remote -v to see where your clone pushes and pulls.

03

Branch

A safe parallel timeline to the main codebase.

A branch is an independent line of commits. You use it to build a feature or fix a bug without touching the stable code on main. Under the hood a branch is just a lightweight pointer to a commit, so creating one is nearly instant. Make them freely.

$ git switch -c feature/navbar   # create + move to it
$ git branch                     # list branches

Considerations

  • Use one branch per feature or fix, with descriptive names like feature/navbar or fix/login-redirect.
  • Keep branches short-lived. The longer one lives, the further it drifts from main and the bigger the merge conflicts get.
  • Protect main on GitHub with branch protection rules so changes arrive only through reviewed pull requests.
  • Delete branches after they're merged to keep the list tidy. The commits stay in history.

04

Commit

A snapshot + message describing your changes.

A commit is a saved snapshot of your project with a message explaining why it changed. Changes first go to the staging area (git add), so you choose exactly what goes into each snapshot. Every commit gets a unique ID (a hash) and points to its parent, and that chain of commits is your project's timeline.

$ git add index.html
$ git commit -m "Add navbar"

Considerations

  • Keep commits small and focused, one logical change each. They're easier to review, revert and understand later.
  • Write messages in the imperative mood ("Add navbar", not "added stuff"). Aim for a subject line of about 50 characters.
  • Check git status and git diff --staged before committing so nothing surprising sneaks in.
  • Never commit secrets (API keys, passwords). Deleting them in a later commit doesn't remove them from history.

05

Push / Pull

Upload to / download from the hosted repository.

Push sends your local commits up to the hosted repository so teammates can see them. Pull downloads new commits from the hosted repository and merges them into your current branch (it's a git fetch followed by a git merge). Together they keep your machine and GitHub in sync.

$ git push origin feature/navbar
$ git pull                  # fetch + merge

Considerations

  • Pull before you start work and before you push. Staying current keeps conflicts small.
  • A rejected push usually means someone pushed first. Pull (or git pull --rebase), then push again.
  • Avoid git push --force on shared branches because it can erase teammates' work. If you must, use --force-with-lease.
  • git fetch downloads without merging, so you can look before you leap.

06

Diff

The visual difference between two versions of code.

A diff shows exactly what changed between two versions of your code, with removed lines in red and added lines in green. You can diff two branches, two commits, or your working files against the last commit. Diffs are the backbone of code review: every pull request is essentially a diff with a conversation attached.

$ git diff            # unstaged changes
$ git diff --staged   # staged changes
$ git diff main...feature/navbar

Considerations

  • Plain git diff only shows unstaged changes. Add --staged to see what's queued for the next commit.
  • Three dots (main...feature) shows only what changed on the feature branch since it split off, which is what a PR shows.
  • Whitespace and line-ending changes create noisy diffs. A formatter (and git diff -w) helps.
  • Read your own diff before asking for review. You'll catch leftover debug code and typos.

07

Merge

Combine a branch back into another branch.

Merging brings the commits from one branch into another, usually a finished feature branch back into main. If both branches have new commits, Git creates a merge commit with two parents that ties the histories together. If main hasn't moved, Git simply fast-forwards the pointer.

$ git switch main
$ git merge feature/navbar

Considerations

  • Merging is non-destructive: no existing commits change, so it's always safe on shared branches.
  • Lots of merge commits can make history noisy. That's the trade-off against rebasing.
  • On GitHub, PRs can be merged three ways: a merge commit, squash (one tidy commit), or rebase. Teams usually pick one.
  • Pull the latest main before merging, and run the tests afterwards.

08

Rebase

Replay your commits on top of the latest main.

Rebasing moves your branch so it starts from the newest commit on main, replaying your commits one by one on top. The result is a clean, straight-line history, as if you'd started your work today. Because every replayed commit is brand new (with a new hash), rebasing rewrites history.

$ git switch feature/navbar
$ git rebase main
$ git push --force-with-lease  # only if already pushed

Considerations

  • The golden rule: never rebase commits other people have already pulled. Rebase your own branches, not shared ones like main.
  • Conflicts can come up once per replayed commit. Fix each one, then run git rebase --continue. git rebase --abort bails out.
  • Interactive rebase (git rebase -i) lets you squash, reword and reorder commits before opening a PR.
  • Not sure? Merging is always the safe option. Rebasing is a tidiness tool.

09

Merge conflict

Two changes touched the same lines; you choose.

A merge conflict happens when two branches change the same lines, or one deletes a file the other edited, and Git can't safely pick a winner. Git pauses the merge, marks the competing versions inside the file, and waits for you to decide what the final code should be. Conflicts are normal. They aren't errors.

$ git status           # lists conflicted files
# edit the file, remove the markers
$ git add index.html
$ git commit

Considerations

  • Remove every <<<<<<<, ======= and >>>>>>> marker. Leftover markers will break your code.
  • The right answer is often a combination of both sides, not one or the other. Talk to whoever wrote the other change.
  • Editor tools like VS Code's merge editor ("Accept Current / Incoming / Both") make this much easier.
  • Panicking? git merge --abort puts everything back. Merging main into your branch often keeps conflicts small.

10

Pull Request

"Please review and merge my branch."

A pull request (PR) proposes merging your branch into another one, usually main. It bundles your diff, a description and a discussion thread, so teammates can review the code, request changes, run automated checks and finally merge. PRs are a GitHub feature rather than part of Git itself. GitLab calls them "merge requests".

$ git push -u origin feature/navbar
$ gh pr create --base main --fill

Considerations

  • Small PRs get reviewed faster and more carefully. Aim for one focused change.
  • Explain what and why, how to test it, and include screenshots for UI changes.
  • Open a draft PR early to get feedback before the work is finished.
  • Write Fixes #42 in the description to link an issue and close it automatically on merge.

11

Issue

A ticket: bug, feature, or task.

An issue is a ticket for tracking work: a bug report, a feature request or a task. Each issue gets a number, a discussion thread, labels and an owner, and it can be linked to the pull request that resolves it. GitHub Projects can then arrange issues into boards and roadmaps.

$ gh issue create --label bug   # prompts for a title
$ gh issue list

Considerations

  • Write a good bug report: steps to reproduce, expected vs. actual behavior, and screenshots or browser and device info.
  • Search existing issues first so you don't open a duplicate.
  • Use labels, assignees and milestones consistently. Issue templates help everyone report in the same format.
  • Closing keywords like Fixes #42 or Closes #42 in a PR close the issue automatically when the PR merges into the default branch.
